# Multi-view Composer: Material Icons, Button Standard, Step Header, Alignment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Multi-view Composer uses Material Symbols Rounded icons only, its buttons follow the same padding and spacing rules as the Main Window action bar, the step headers keep their numbers and show a check after the label, "Back to displays" shares one right edge with everything in the right rail, and step 3 says "Save & Apply".

**Architecture:** Reuse what round 3 built: `MaterialIcon` + `Resources/MaterialIcons.xaml` (generated by `tools/icons/import-material-icons.ps1`), `Style.Button.ActionBar` (12 px side padding, 48 px high, 8 px icon gap) and `Style.Banner`/overlay scrollbar styles. The Composer's secondary buttons move to one new outlined variant of the action-bar style. `StepHeader` keeps its number and gains a trailing check. The right rail loses its scrollbar gutter (overlay scrollbar) so cards and the pinned cluster share one right edge. User-visible "Take" wording changes; code identifiers (`TakeAsync`, `CanTake`, `Style.Button.Take`, `Brush.Action.Take`) do not.

**Tech Stack:** .NET 8 WPF, WPF-UI 4.3.0 (controls only; the Fluent icon font is being retired), xUnit STA tests in `tests/AvasRoutingTool.Tests`.

**Spec:** User feedback 2026-11-07 with `docs/superpowers/specs/assets/2026-11-07-composer-feedback-back-button.png` and `...-steps.png`; rules from `docs/superpowers/plans/2026-11-07-main-window-action-bar-and-material-icons.md`; locked decisions in `docs/superpowers/handoff/2026-11-04-ui-round3-handoff.md`; Composer behaviour in `docs/superpowers/specs/` (Composer spec, section "Stage, then Take").

## Global Constraints

- WPF-UI controls only; touch 48 px (36 px compact); font floor 12 px; accent roles; no hard-coded colours (`UiV2Guards` allowlist is not widened).
- Button standard (from the Main Window): `Size.Action.PadX` 12 each side (`Size.Action.Padding` = `12,0`), `Size.Touch.Min` 48 high, `Size.Space.Action` 8 between an icon and its label and between neighbouring buttons, label `Font.Size.Body` SemiBold, icon `Size.Icon.Layout`.
- Composer secondary buttons are outlined (2 px, `Brush.Border.Control`), not ghost. `Take` (`Style.Button.Take`) stays the big filled primary and text-only, 72 px high, untouched except its label.
- Brand mark and `LayoutSchematic` stay custom. No other view is touched (Room Cameras, PTZ pad, Advanced, Settings are later rounds).
- Material icons are imported only from `raw.githubusercontent.com/google/material-design-icons` by the existing script; Apache-2.0 notice stays in `THIRD-PARTY-NOTICES.md`.
- Never merge to `main`, never push. Floor window 1024x720, target 1920x1080, dark and light themes.
- Test command base: `dotnet test tests/AvasRoutingTool.Tests/AvasRoutingTool.Tests.csproj -p:BaseOutputPath=bin/r9/ ... -- RunConfiguration.DisableParallelization=true`. Env-gated screenshots need `AVAS_UIV2_SHOTS` set in the same shell command.

## Wording decision: "Save & Apply" (validated)

What the button does today (`MultiViewComposerViewModel.TakeAsync`): sends the whole staged picture to the display at once (`set:multiview`), commits it as the live draft, and offers Undo for `UndoWindow`. It stores no named preset; unsent edits are kept automatically as a draft on the display card when the Composer closes.

Verdict: the user's wording is accepted, with two rules. (1) "Apply" is the part that tells an operator the surgeon's screen changes now, so the label is never shortened to "Save" alone. (2) "Save" must not collide with the existing "DRAFT · Resume" chip, so the draft wording is left as it is. Not verified: whether the hardware keeps the layout after the display powers off, so no text promises that.

| Where | Now | New |
|---|---|---|
| Step 3 heading | CHECK, THEN TAKE | CHECK, THEN SAVE & APPLY |
| Main button | TAKE n CHANGE(S) TO SCREEN | SAVE & APPLY n CHANGE(S) |
| Main button (layout only) | TAKE NEW LAYOUT TO SCREEN | SAVE & APPLY NEW LAYOUT |
| Busy label | Sending to X... | Applying to X... |
| Success banner | On screen | Saved & applied - on screen now. |
| Failure banner | Take failed: {msg} Check what is on screen. | Could not apply: {msg} Check what is on screen. |
| Step 3 screen-reader text | Step 3, Check, then take: ready / not ready | Step 3, Check, then save and apply: ready / not ready |
| Step 3 help text, canvas hint, display-card note (`DisplayCardView.xaml:668`) | ...until you press Take / until Take | ...until you press Save & Apply / until Save & Apply |
| Blocked reasons, tooltips, banners that name the button | "Take" | "Save & Apply" (the implementer greps user-visible strings; identifiers and log text stay) |

## Review Focus

1. 264 px right rail at 1024 wide: "SAVE & APPLY 3 CHANGES" and the long Undo label wrap inside their buttons; nothing clips, the 48 px height holds (Task 0 and Task 2 tests).
2. Right rail scrolls (many change lines): the shared right edge still holds and the overlay scrollbar never hides button text (Task 4).
3. Step 3 done while busy: label reads "Applying to X..." and the step header stays consistent (Task 0, Task 3).
4. Light theme: the number on the filled "done" circle and the check after the label stay readable (Task 3).
5. Compact Replace/Move strip on the smallest block (PIP inset): 36 px high, text and icon not clipped, strip may overhang the block as today (Task 2).
6. Icon sizing trap: `MaterialIcon` is sized by `Width`/`Height`, not `FontSize`; every converted setter must change (Task 1).

## Execution advice

Subagent-driven, one Sonnet implementer and one read-only Sonnet QA reviewer per task, run strictly in the order 0, 3, 1, 2, 4, 5. The tasks touch the same two XAML files (`MultiViewComposerView.xaml`, `Composer.xaml`), so no two run at once. Task 3 comes before Task 1 only because the new check icon (`check`) already exists; Task 1 then converts everything else. Tasks 1 and 2 carry the most risk (`FontSize` to `Width`/`Height`, and the Composer button styles feed many tests), so their QA reviewer also checks the Review Focus lines. A final whole-branch QA reviews against this plan.
